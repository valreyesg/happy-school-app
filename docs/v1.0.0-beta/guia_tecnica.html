08 Variables de Entorno

Este documento describe cada variable de entorno necesaria para desplegar en producción. El backend se puede alojar en Railway o Render; el frontend web en Vercel o Netlify.

Backend — backend/.env

En desarrollo mobile, usar la IP de la computadora en la red local (no localhost), porque el celular no puede acceder a localhost de la computadora.

Cómo configurar en Railway

  1. Entrar a railway.app
  2. Ir al proyecto → pestaña Variables
  3. Agregar cada variable una por una
  4. Railway reinicia el servidor automáticamente al guardar

Cómo configurar en Vercel

  1. Entrar a vercel.com
  2. Proyecto → Settings → Environment Variables
  3. Agregar VITE_API_URL con el valor de producción
  4. Nuevo deploy después de guardar

Notas de seguridad

  • Nunca subir archivos .env al repositorio de Git
  • Los secretos deben ser únicos entre desarrollo y producción
  • La DATABASE_URL de producción no debe compartirse por correo o WhatsApp
  • Rotar las claves si se sospecha que fueron expuestas

09 Guía de Migraciones en Producción

Las migraciones son archivos SQL que crean o modifican la estructura de la base de datos. Deben aplicarse en orden numérico exacto. Hay 49 archivos de migración en backend/migrations/. La herramienta usada es node-pg-migrate.

Comandos disponibles (desde backend/)

bash 
# Aplicar todas las migraciones pendientes
npm run migrate

# Revertir la última migración aplicada
npm run migrate:down

# Cargar datos iniciales (seed)
npm run seed

Primer deploy — base de datos vacía

Paso 1 — Verificar la variable DATABASE_URL

bash 
cd backend
node -e "const { Pool } = require('pg'); const p = new Pool({connectionString: process.env.DATABASE_URL}); p.query('SELECT NOW()').then(r => console.log('Conexión OK:', r.rows[0])).catch(e => console.error('Error:', e.message));"

Paso 2 — Aplicar todas las migraciones

bash 
cd backend
npm run migrate

Deberías ver algo como:

output 
> node-pg-migrate up
Connecting to database...
Running migration: 001_schema_inicial
Running migration: 002_unique_constraints
...
Running migration: 049_plantillas_whatsapp_faltantes
Migrations applied successfully.

Paso 3 — Cargar datos iniciales (seed)

bash 
cd backend
npm run seed
El seed solo debe correrse UNA VEZ en una base de datos nueva. Correrlo de nuevo en una BD con datos podría causar duplicados.

Actualización a nueva versión

  1. Hacer backup antes (ver Plan de Respaldo)
  2. Desplegar el nuevo código
  3. Ejecutar npm run migrate — detecta automáticamente cuáles migraciones ya se aplicaron y solo ejecuta las nuevas
  4. Reiniciar el servidor si es necesario

Qué hacer si una migración falla

  1. Leer el mensaje de error completo
  2. Verificar el estado de migraciones:
sql 
SELECT * FROM pgmigrations ORDER BY run_on DESC LIMIT 10;

Si el error es "relation already exists": la migración ya fue aplicada. Marcarla manualmente:

sql 
INSERT INTO pgmigrations (name, run_on)
VALUES ('nombre_de_la_migracion', NOW());
Cualquier error desconocido: restaurar desde backup y contactar a Valeria.

Lista de migraciones (referencia)

sql

10 Plan de Respaldo de Base de Datos

La base de datos contiene toda la información de la escuela. Sin respaldo reciente, un fallo podría significar pérdida irreversible.

Respaldo manual (pg_dump)

bash 
# Exportar toda la base de datos
pg_dump "$DATABASE_URL" -Fc -f backup_$(date +%Y%m%d_%H%M%S).dump
ParámetroSignificado
$DATABASE_URLURL de conexión PostgreSQL
-FcFormato custom de PostgreSQL
-fNombre del archivo de salida

Alternativa en formato SQL legible:

bash 
pg_dump "$DATABASE_URL" --no-owner --no-acl > backup_$(date +%Y%m%d).sql

Guardar el respaldo

  1. Descargarlo a tu computadora
  2. Subirlo a Google Drive o nube personal
  3. Nombrado recomendado: happy_school_YYYYMMDD.dump

Frecuencia recomendada

PeríodoCuándo hacer backup
Durante el pilotoCada semana (mínimo)
Después del pilotoAntes de cada actualización
Producción estableAutomatizado cada 24 horas (Railway plan pagado)

Restaurar desde un backup

bash 
# Restaurar desde archivo .dump
pg_restore -d "$DATABASE_URL" --no-owner --clean backup_YYYYMMDD.dump

# Restaurar desde archivo .sql
psql "$DATABASE_URL" < backup_YYYYMMDD.sql
Advertencia: La restauración sobrescribe los datos actuales. Solo usar en emergencias.

Verificar que el backup es válido

bash 
pg_restore --list backup_YYYYMMDD.dump | head -20

Si muestra una lista de tablas y objetos, el backup está bien formado.

Backup automático en Railway

Railway ofrece backups automáticos en sus planes de pago:

Dashboard → Base de datos → Backups

Los backups se guardan por 7 días en el plan básico.

11 Plan de Rollback

Regla de oro: Siempre hacer backup antes de cualquier deploy. Sin backup, el rollback de BD no es posible.

Escenario 1 — El backend no arranca después del deploy

Error 500 / sin respuesta API devuelve error 500 o no responde
  1. Revisar logs:
    Railway: Dashboard → Deployment → View logs
    Render: Dashboard → Logs
  2. Si es variable de entorno faltante: agregarla y redeploy
  3. Si es error de código: hacer rollback desde el dashboard
    • Railway: Deployments → seleccionar deploy anterior → "Redeploy"
    • Render: Manual Deploys → seleccionar versión anterior

Escenario 2 — Una migración de BD falló a mitad

Error SQL Funcionalidades no funcionan, logs muestran errores SQL
  1. No hacer más cambios hasta resolver
  2. Verificar qué migraciones se aplicaron:
sql 
SELECT name, run_on FROM pgmigrations ORDER BY run_on DESC LIMIT 5;
  1. Opción A: npm run migrate:down (solo si es la última)
  2. Opción B: restaurar desde backup previo al deploy
  3. Corregir el script y volver a intentar

Escenario 3 — El frontend web no carga o muestra errores

Frontend La web no carga o muestra errores en producción
  1. Verificar que VITE_API_URL en Vercel apunta al backend correcto
  2. Rollback desde Vercel: Deployments → deploy anterior → "Promote to Production"
  3. Si es variable de entorno: corregirlas y redeploy

Escenario 4 — Datos corruptos o borrados accidentalmente

Pérdida de datos Datos incorrectos o eliminados en producción
bash 
pg_restore -d "$DATABASE_URL" --no-owner --clean backup_YYYYMMDD.dump

Si el backup también tiene datos incorrectos, buscar un backup más antiguo.

La restauración borrará todos los datos agregados después de la fecha del backup. Evaluar antes de proceder.

Escenario 5 — La app mobile deja de funcionar

Mobile La aplicación móvil deja de responder o muestra errores
  1. Verificar si el backend está funcionando (probar la URL de la API en el navegador)
  2. Si el backend caído es la causa → resolver primero el backend (Escenario 1)
  3. Si está en Expo Go: los usuarios recargan la app
  4. Si está en build nativo (APK): publicar una versión de corrección

Cómo hacer rollback de código en Railway

  1. Entrar a railway.app
  2. Ir al proyecto → servicio del backend
  3. Clic en "Deployments"
  4. Buscar el último deploy exitoso
  5. Clic en "…" → "Redeploy"

Cómo hacer rollback de código en Vercel

  1. Entrar a vercel.com
  2. Ir al proyecto del frontend
  3. Clic en "Deployments"
  4. Buscar el último deploy exitoso
  5. Clic en "…" → "Promote to Production"
